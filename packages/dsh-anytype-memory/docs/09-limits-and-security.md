# 09 限制与安全

## 本文回答什么问题

- 插件面对的 Anytype v2 API 有哪些**硬边界**（缺什么端点、什么会 404、什么会漂移），以及插件如何绕过而不是假装没有；
- 在「持续 1 req/s」这类真实约束下，一次召回/一次写入的**预算**是多少，插件为什么**不做自动重试与退避**；
- 哪些动作是**破坏性**的，为什么插件一律不物理删除；
- 并发写冲突如何自愈、幂等键的精确语义、什么必须交给 agent 裁决；
- 密钥与记忆内容**流向哪里**，以及**记忆投毒**这一具体攻击面如何被缓解、缓解不了什么；
- 已知限制清单与每条限制的验证方式。

## 阅读前置

- 读过 02（记忆模型）与 01（架构）最佳；至少要知道 `memory` 对象、`memory_scope` 关系、`memory_embedding` 属性的位置。
- 本文中「Anytype v2 事实」一节的观测时间为 **2026-10-23**，环境为 `http://127.0.0.1:31009` 上的 pre-release 构建（`Anytype-Version: 2025-11-08`）。API v2 是 pre-release，**能力面可能随构建漂移**——本文所有端点结论都应以本机运行时自省为准。

## ① API 能力边界

> **与 05 文档的分工**：05（Anytype 就是索引）从「Anytype 替代了本地索引的哪些部分」的角度列出三条缺口（**无相关度分数** / **无向量端点** / **中文分词质量未知**）；本文从「**端点与字段的缺失**」这一层列边界。两者互补——本文只补 05 没写的端点层事实，不重复论证替代方案。

### 1.1 v2 是 pre-release：能力面必须运行时自省

v2 API 的官方声明是 **「可以在不升 API 版本的情况下改变」**（can change without a new API version）。这意味着**任何写死在插件里的端点/字段假设都会腐坏**。

**插件的对策：运行时自省优先于硬编码。**

| 自省入口                    | 用途                                                  | 何时调用                   |
| --------------------------- | ----------------------------------------------------- | -------------------------- |
| `GET /v2/docs/openapi.json` | 拉全量 operation 清单（活体 55 个 operation）         | `memory_doctor` 启动自检时 |
| `GET /v2/schemas`           | 列出可用 schema kind                                  | `memory_doctor`            |
| `GET /v2/schemas/{kind}`    | 取某个 kind 的字段/结构定义（如 `filters`、`search`） | 遇到不确定的请求体形状时   |
| `GET /v2/schemas/ops/{op}`  | 取单个编辑 op 的成员结构                              | 需要构造 ops 数组时        |

**落地规则**：

1. 插件**不硬编码**「某 operation 一定存在」——所有能力假设在 `memory_doctor` 里探测，探测结果进当次运行的诊断结论；
2. 插件**硬编码**的只有「v2 基础动词」：`GET/POST/PATCH/DELETE /v2/spaces/...`、`POST /v2/spaces/{id}/search`、上述四个 schemas 端点、`GET /v2/auth/whoami`；
3. 探测失败**不阻塞插件**：能力缺失降级为「该能力不可用」并如实上报，不静默吞掉；
4. **任何以本仓库文档为唯一依据的端点结论都视为过期风险**——升级 Anytype 后先跑 `memory_doctor`。

### 1.2 没有 backlink 端点

HTTP v1/v2 **不存在 backlink 端点**。Anytype 内部 gRPC 有 `NavigationGetObjectInfoWithLinks`，但**未在 HTTP 侧暴露**。

**插件的对策**：用空间**原生关系属性** `links(objects)` / `backlinks(objects)` 做反向边查询——这两个是 Anytype 自身维护的关系属性，可以通过 `fields` 投影读回。

| 想做的事                  | 可行路径                                                                                     | 代价                                       |
| ------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------ |
| 「谁指向了 M1」           | 读 `backlinks` 关系属性 → 客户端侧过滤出指向 M1 的对象                                       | 读回的是**全空间反向边**，过滤在客户端做   |
| 「M1 指向了谁」           | 直接读 M1 的 `links` 关系属性                                                                | 无需额外往返                               |
| 「召回时的关系臂」        | `filter='backlinks IS NOT EMPTY'` 收窄，或 `fields=["links","backlinks"]` 投影后本地扩展一跳 | 服务端过滤能力缺失时只能全量拉取再本地过滤 |
| 「M1 被提及的全部上下文」 | 受控边 `mentions` + `derived_from` 正读，反向靠 `backlinks` 过滤                             | 同上                                       |

**能力探测**：`memory_doctor` 会探测「relation 过滤是否被服务端接受、能否匹配到行」——
用**真实存在**的记忆对象 id 做 `memory_relates_to IN ("<id>")` 过滤。

> **活体实测（2026-10-23）**：请求 **200**（服务端**接受**该 filter，不报错），
> 但 **`total=0`**——匹配不到任何行。故关系臂的**兜底**不是「换个 filter 再试」，
> 而是**投影 Anytype 原生的 `links` / `backlinks`**（双向关系自动生成），把邻居 id
> 作为 `related_ids` 返回给 agent。`memory_doctor` 把这件事报成
> `capabilities.relation_filter_rows = 0` 并附告警。

**已知副作用**：反向边查询的结果集规模与空间对象数同阶，**分页 `total` 只是下界**（见 1.6 与 ⑦），因此反向边查询必须**收窄**（按 `memory_scope` / `memory_kind` / `memory_status` 过滤后再取），不允许无过滤全量拉取。

### 1.3 没有 AI 端点

HTTP v1/v2 **不存在 AI 端点**。上游 gRPC 里的 AI RPC 被标注为 **「mock AI RPCs … Not implemented in main」**。

**插件的对策（也是整个插件的立身之本）**：

- 插件**永不**在进程内调用模型。所有语义工作——从对话里抽记忆、判两条记忆是否重复、给一段内容写摘要、把文本变成向量、对候选集重排——**全部通过工具调用委派给外部 agent**；
- 插件提供的是**协议与容器**：`memory_candidates`（给候选）、`memory_set_embedding`（收向量）、`memory_suggest_links`（给建议）、`memory_review`（收裁决）；
- 插件自身对 embedding 只做**算术**：base64 解码 `memory_embedding` 属性（`Float32Array` 小端）、校验 `memory_embedding_dim` 与 `memory_embedding_model`、在候选集上线性算余弦相似度。**文本 → 向量**这一步是模型，必须由 agent 完成。

**顺带的好处**：Anytype 本身是 fully offline / local-first 的，可运行在**纯本地模式**（不开启同步）。这意味着整个记忆栈可以**完全不出本机**——见 ⑤。

### 1.4 单属性端点 404

在本机 pre-release 构建上，`GET /v2/spaces/{id}/properties/{key}` **返回 404**——属性只能**列举**，不能单独取。

**插件的对策**：

- 属性面的所有读取一律走 `GET /v2/spaces/{id}/properties`（列表端点）后客户端侧筛选；
- 插件**不**把单属性 GET 放进任何热路径（写入后校验、召回、doctor 都不走它）；
- 若未来构建修复该端点，行为不变（列表端点始终可用），无需迁移。

> `[待活体验证]` 该 404 是否为构建缺陷还是有意设计，尚无上游说明。验证方式：`curl -i -H "Authorization: Bearer $KEY" http://127.0.0.1:31009/v2/spaces/$SPACE/properties/<真实 key>`，对比 `GET /v2/spaces/$SPACE/properties` 中同 key 的存在性。

### 1.5 v1 / v2 差异与「本插件锁定 v2」

v1 与 v2 在对象模型、编辑 ops、鉴权头、错误体上都有实质差异（v1 有 tags 与独立 options CRUD，v2 的 options 只能内联铸造；v1 无 `Anytype-Version` 头语义等）。

**本插件锁定 v2，不做 v1 兼容层。** 理由：

1. v2 是 Anytype 当前的开发主线，能力面更全（`fields` 投影、紧凑 `filter` 语法、`dry_run`、`Idempotency-Key` 覆盖面更广）；
2. 双版本适配会让工具契约出现「同一参数两套语义」，agent 侧难以推理；
3. 插件基址与版本头都由用户显式配置（`baseUrl` / `apiVersion`），需要 v1 时**换一个插件实例**即可，而不是在一个工具面里分叉。

所有请求固定携带 `Authorization: Bearer <key>` 与 `Anytype-Version: <version>`，路径一律 `/v2/` 前缀。

### 1.6 分页语义（影响所有「总数」类推断）

| 事实                                                                   | 后果                                                                       |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `?offset=&limit=` 分页，**默认 limit = 25**，**上限 1000**             | 单批最多取 1000 条；`limit=1000` 已是天花板                                |
| 全文检索返回的 `total` 是**下界**（lower bound），只要 `has_more` 为真 | **不得**把 `total` 当精确计数；`memory_stats` 的计数口径必须标注为「下界」 |

`memory_stats` 因此只承诺**基于已枚举分片的精确计数**与**检索侧的下界计数**两个口径，并在返回值里显式区分（例如 `total_is_lower_bound: true`），避免下游把下界当事实。

### 1.7 没有相关度分数：只有有序 rows

`POST /v2/spaces/{id}/search` 的响应里**没有** `_score` 之类的分数字段——只有**有序的 rows**。

**后果与对策**：

- 插件**不能**把不同臂的分数直接相加（不同臂的分数尺度不可比，甚至根本没有分数）；
- 融合必须走 **RRF（`k = 60`）**——只吃**名次**不吃分数：`score_rrf(d) = Σ_arms 1 / (k + rank_arm(d))`，某臂没命中则该臂不贡献分数；
- 跨臂的「谁更相关」只能由**插件自算的乘性 boost**（recency / confidence / proof 三个因子）补充，而不是靠服务端的分数。

这条限制是**好设计**：它逼着召回走名次融合，天然免疫「不同检索路分数不可比」这个经典坑。

### 1.8 属性命名、字段表与类型布局（活体实测 2026-10-23）

这三条是**真实 Anytype 桌面端**（`Anytype-Version: 2025-11-08`）才暴露的，单元测试完全抓不到。

#### 1.8.1 同名不同格式会 400 → 属性一律带 `Memory ` 前缀

空间自带一批**内置属性**（实测 **41 个**）：

| 内置属性                                         | 格式           | 与插件的冲突                                     |
| ------------------------------------------------ | -------------- | ------------------------------------------------ |
| `origin`                                         | `number`       | 插件想铸 `select` 的 `Origin` → **400**          |
| `source`                                         | `url`          | 插件想铸 `objects` 的 `Source` → **400**         |
| `status`                                         | `select`       | 插件想铸 `select` 的 `Status` → **同名不同定义** |
| `tag`                                            | `multi_select` | 插件**直接复用**（唯一例外）                     |
| `links` / `backlinks`                            | `objects`      | 原生双向关系，关系臂兜底依赖它                   |
| `assignee` / `creator` / `due_date` / `done` / … | 各不相同       | 朴素显示名一律避开                               |

**服务端报错形态**：**400 `property format conflict`**，issues 指到
`/type_properties/N/format`，提示「omit format to use the existing property as
it is, or create a new property under a different key」。

**插件的对策**：

| 规则       | 内容                                                                                           |
| ---------- | ---------------------------------------------------------------------------------------------- |
| 显示名前缀 | 插件自有属性一律 `Memory ` 前缀（key 派生为 `memory_*`）                                       |
| 唯一例外   | `tag` —— **复用内置 `tag(multi_select)`**，不另造 `memory_tag`（不污染词表，也更符合用户直觉） |
| 同名已存在 | bootstrap 铸属性时**省略 `format`**（沿用既有定义），并把格式差异写进 `warnings[]`             |

#### 1.8.2 字段表 = 类型文档的 dataview 块

> **类型的字段表 = 类型文档 `blocks[0]`（dataview）的 `properties[]`**。
> `GET /v2/spaces/{id}/types/{key}` 返回的类型文档里，第一个块是 dataview，它的
> properties 列表就是字段表。

**不在字段表里的属性**：「**会被存储并随对象返回，但按类型过滤/查询时该键被拒绝**」
（服务端原话："the value is stored and served on the object, but type-scoped search
and queries over X refuse the key"）。

| 后果                                                                                        |
| ------------------------------------------------------------------------------------------- |
| `filter: memory_kind IN (...)` 这类**按类型收窄**直接失效（键被拒绝，条件被丢弃或整体报错） |
| 写入本身不报错——所以「写成功了但过滤不生效」是极难排查的一类故障                            |

**插件的对策**：

| 步骤 | 动作                                                                                                             |
| ---- | ---------------------------------------------------------------------------------------------------------------- |
| ①    | 建类型时带 `property_definitions`（字段随类型一起铸）                                                            |
| ②    | 对**已存在**的类型，读类型文档取字段表，把缺失属性用 `add_property` op 挂进去                                    |
| ③    | **`add_property` op 只认 `property`（key）+ `format`**，不认 `name`（传 `name` 报 `json: unknown field "name"`） |
| ④    | **建完类型必须重新盘点属性**——建类型会顺带把字段铸成空间属性，继续按旧清单建会撞 `property key already exists`   |

**紧凑类型列表读不到字段表**：`GET /v2/spaces/{id}/types` 只给类型自身属性
（name / creator / …），字段表必须**逐个读类型文档**。

#### 1.8.3 记忆类型布局必须是 `basic`

| 布局       | 标题（`properties.name`） | 结论                                     |
| ---------- | ------------------------- | ---------------------------------------- |
| `note`     | **丢失**（被当成正文块）  | 禁用——正文多出一段，标题能力直接消失     |
| `basic`    | 保留                      | **采用**——记忆条目的「一行事实」就是标题 |
| `todo`     | 保留                      | 可用但语义不符                           |
| `bookmark` | 保留                      | 可用但语义不符                           |

记忆类型与作用域类型的布局都是 `basic`。bootstrap 对**已存在**的类型会
`PATCH` 校正布局（失败只告警，不中断）。

### 1.9 中文全文检索可用，但索引是最终一致的

| 事实                                                                                                                                          |
| --------------------------------------------------------------------------------------------------------------------------------------------- |
| ✅ **中文全文检索可用**：中文短语（如「持久记忆」「索引全部交给」「拒绝」）能命中对象；**标题与正文都参与索引**                               |
| ✅ 此前担心的「中文分词失效」被**证伪**：SQLite FTS5 的 `unicode61` 对中文失效是事实，但 **Anytype 桌面端自己的检索不走那条路**               |
| ⚠️ **但对生僻词/未登录词不可靠**：用生僻词（观澜 / 蓑笠 / 孤舟 …）做探针时，对象**已进索引**（同对象的 ASCII 标记可命中）而**中文短语搜不到** |
| ⚠️ **全文索引是最终一致的**：刚创建的对象**搜不到**，实测约 **3～6s** 后才可被检索命中，且偶发更久                                            |

**插件的对策**：

1. `memory_doctor` 的中文自检**必须轮询重试**（当前实现：最多 **8 次**、每次间隔 **1500ms**），返回 `attempts` 与 `latency_ms`；
2. **双探针**（同一探针对象里放一段中文短语 + 一段 ASCII 标记），据此给出三态 `verdict`——
   - `chinese_recall_ok`：中文命中 → 中文召回可用；
   - `chinese_tokenization_issue`：ASCII 命中而中文没命中 → **中文分词对该词不可靠**（不是索引滞后）；
   - `index_lag_or_unindexed`：两者都没命中 → **索引滞后**（隔几秒重跑确认）；
3. **探针短语必须用常用词**——否则会把「分词对生僻词不可靠」误判成「中文根本没被索引」；
4. agent 侧「写完立刻自查能否召回」要留缓冲：刚写的对象可能搜不到。

### 1.10 同一个 etag 只能写一次

| 事实                                                                                           |
| ---------------------------------------------------------------------------------------------- |
| 连续两次 `PATCH`（即便两次都带**同一个** `If-Match` etag），第二次必得 **409 `etag_mismatch`** |

**插件的对策**：多字段变更**合并进同一个 `set_properties` op**（一次原子写）。
`memory_supersede` 因此把 `memory_valid_to` 与 `memory_status=superseded` 合成一次写。

### 1.11 属性值形状与词表纪律

| 键类型                                                    | 值形状                      |
| --------------------------------------------------------- | --------------------------- |
| 列表型（`select` / `multi_select` / `objects` / `files`） | **数组**（选项名或对象 id） |
| 标量型（`text` / `number` / `date` / `checkbox`）         | **标量**                    |

- `set_properties` 的 `set` 成员同此语义；`add` / `remove` **仅对列表型键有效**；
- **未知属性键 → 400**，服务端会列出已知键并给「did you mean」——拼错的键**不会**被静默铸造；
- **未知 select 选项名 → 400**，除非请求带 `create_missing_options=true`。

**插件的对策**：**受控词表不开** `create_missing_options`（`memory_kind` /
`memory_status` / `memory_origin` / `memory_source_channel`——拼错即报错）；
**开放词表才开**（`tag`——允许新标签自动建选项）。

## ② 限速与预算

### 2.1 服务端限速是硬事实

| 项       | 值                                                                |
| -------- | ----------------------------------------------------------------- |
| 持续速率 | **1 req/s**（sustained）                                          |
| 突发额度 | **60**（burst）                                                   |
| 超限响应 | **429 `rate_limit_exceeded`**                                     |
| 调试开关 | `ANYTYPE_API_DISABLE_RATE_LIMIT=1` 可关闭限速（**仅本机调试用**） |

**429 是预期内的常规事件，不是异常。** 插件对待 429 的方式：

| 场景         | 插件行为                                                                               | 调用方（agent）期望                                                              |
| ------------ | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 读请求遇 429 | **不自动重试**，原样抛出（`status=429`、`code=rate_limit_exceeded`、`hints` 一并透传） | 读天然幂等，下一轮自行重放即可                                                   |
| 写请求遇 429 | **不自动重试**，原样抛出                                                               | 用**同一个** `idempotency_key` 重放同一次请求 → 服务端重放已存响应，不会重复写入 |
| 连续 429     | 不做本地排队/退避                                                                      | 放缓调用节奏（例如合并批次）后重放                                               |

### 2.2 批量读纪律

| 纪律                       | 具体要求                                                                                                         |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **单次召回 HTTP 往返 ≤ 3** | 见 2.3 的三臂预算表                                                                                              |
| **禁止逐对象 GET 循环**    | 拿到候选 id 列表后**不得**逐个 `GET /v2/spaces/{id}/objects/{oid}`；必须用 `fields` 投影或列表端点批量取回       |
| **一次多取**               | 列表端点 `limit` 拉满（`memory_list` 上限 100、`memory_search` 服务端上限 1000），配合 `fields` 只投影需要的属性 |
| **收窄先于拉取**           | 先用 `filter`（紧凑过滤语法）或 `memory_kind` / `memory_status` / `memory_scope` 过滤缩小结果集，再分页          |
| **token 预算是一等公民**   | 召回按 `max_tokens` 截断并如实报告 `truncated` / `omitted_count`——「有东西没召回」必须让 agent 看得见            |

### 2.3 单次召回的请求预算

`memory_recall` 的三臂各占**一次** HTTP 往返，合计**最多 3 次**（三臂可并发发起，故串行等待的最坏情况是 3 次）：

| 臂                  | 手段                                                                                                                                                    | 单次往返内完成的事                                          |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| **lexical**（词法） | `POST /v2/spaces/{id}/search`（`query` + `filter` 限 `memory_kind` / `memory_status` + `sorts` + `fields` 投影）                                        | 取回按相关度排序的候选                                      |
| **vector**（向量）  | `POST /v2/spaces/{id}/search` 取 top-M → `fields` 投影 `memory_embedding` / `memory_embedding_dim` / `memory_embedding_model` → 本地 base64 解码 → 余弦 | 取回候选向量并排序；模型/维度不符者剔除并在结果中报告剔除数 |
| **links**（关系）   | 先按受控边属性过滤（`memory_relates_to IN (...)` 等）；命中 0 行则**用已投影的 `links` / `backlinks` 兜底**取邻居 id                                    | 取回关系邻域候选                                            |

**硬纪律**：

- **严禁**「先 search 拿 id 列表再逐个 GET」的循环——需要正文时用 `fields` 投影一次取回；
- **向量召回在候选集上线性计算**——Anytype v2 **没有 ANN / 向量索引端点**（见 ⑦）。因此候选集必须**事先收窄**（按 `memory_scope` / `memory_kind` / `memory_status` / `memory_confidence` 过滤后再取批），候选集规模超限时插件**不静默截断**，而是返回可操作提示（请收窄过滤条件），避免「看起来召回了其实只看了前 N 条」；
- 线性计算复杂度为 O(候选数 × 维度)，`memory_embedding_dim` 属性记录实际维度，供预算核算；
- 融合用 **RRF**（`k = 60`），融合后再乘性 boost（recency / confidence / proof 三个因子）——排序细节见 05 文档 §5 与 02 文档 §9；
- **召回自测量写回**（命中条目 `memory_access_count` + 1，写回 Anytype）属于**三臂之外的独立写操作**：默认关闭（`bump_access_count=false`），开启时**每次调用封顶 5 条**（限速守卫），失败**不阻断**召回。`[待活体验证]` 验证方式是统计一次 `memory_recall` 触发的请求总数，确认与「三臂 + 至多 5 条自测量写回」相符。

### 2.4 插件不做自动重试与退避（显式决策）

**这是一个有意的留白，不是遗漏。**

**理由**：

1. **重试策略与幂等键的责任归调用方**。不同写操作的幂等性、可重试性与代价差异很大：写一条 `fact` 与写一条 `summary` 都可以重放，但「更新」与「supersede」重放会改变语义状态。内建退避会把这些差异抹平。
2. **插件内建退避会掩盖真实语义**。一次写被静默重试 3 次后成功，调用方看到的是「一次成功」，而真实情况是「服务端拒了 2 次」——这在限速 1 req/s 的环境里恰恰是最需要被看见的信号。
3. **退避会与幂等键语义冲突**。正确重试必须复用同一个 `idempotency_key`；如果插件自己生成/轮换 key，重试就退化成重复写入。**谁生成 key，谁才知道该不该复用它**。
4. **插件的责任边界是提供安全原语**，把「要不要重试、重试几次、隔多久」交给有全局上下文的 agent 层判断。

**插件提供的三件安全原语**（写工具统一暴露）：

| 原语   | 参数              | 映射                 | 语义                                                                                                                                            |
| ------ | ----------------- | -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 预演   | `dry_run`         | `?dry_run=true`      | 只校验并回报，不落库。创建类预演返 **200**（提交返 **201**），更新/删除类预演与提交同为 200，靠响应体 `dry_run: true` 区分                      |
| 防重   | `idempotency_key` | `Idempotency-Key` 头 | 服务端按「key + 请求体」绑定：同 key 同 body 重放已存响应；同 key 换 body 返 **409 `idempotency_conflict`**。**重试同一请求必须复用同一个 key** |
| 乐观锁 | `expected_etag`   | `If-Match` 头        | 携带过期 etag 写入会得 **409**，不会静默覆盖他人改动                                                                                            |

## ③ 写权限与破坏性操作

### 3.1 DELETE 只对本 key 创建的对象有效

| 事实                                                                   | 后果                                                                                                          |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `DELETE /v2/spaces/{id}/objects/{oid}` **只能删本 API key 创建的对象** | 对应用内创建、导入、他人成员创建的对象一律 **403 `not_created_by_this_key`**；`dry_run=true` 预演**也不豁免** |

**插件的对策：一律用归档，不用物理删除。**

| 意图                 | 插件动作           | 落库方式                                                                                |
| -------------------- | ------------------ | --------------------------------------------------------------------------------------- |
| 「这条记忆作废了」   | `memory_archive`   | `memory_status` 置 `archived`，正文与关系保留                                           |
| 「这条被新记忆取代」 | `memory_supersede` | 旧记忆 `memory_status` 置 `superseded` + `memory_valid_to`，并连 `memory_supersedes` 边 |
| 「彻底删除」         | **不提供**         | —                                                                                       |

**唯一例外**：`memory_doctor` 清理**它自己刚创建的探针对象**（本 key 创建 → 删除合法，归档进 Bin 可恢复）。**除此之外，任何流程都不删除记忆对象**——这是插件的不变量 I2。

理由：物理删除在本插件的写入来源分布下**大多数时候不可用**（对象多由应用内或他人创建），提供一条大概率 403 的能力只会制造错误路径；而 `archived` 状态**可逆、可审计、可被召回权重降权**，语义上更贴合记忆的「不活跃」而非「不存在」。

### 3.2 类型 / 属性删除会进 Bin（可恢复）

删除 Anytype 的**类型**或**属性**是**软删除**：对象进入 Bin，可从 Bin 恢复。

**插件的对策**：

- `memory_setup` 是**幂等**的：已存在的类型/属性**跳过**而非重建，绝不「先删后建」；
- 插件**不提供**删除类型/属性的工具面——`memory_setup` 只做「确保存在」，schema 演进走新增属性 + 迁移记忆值，不走删除；
- 确需清理 schema 时，由用户在 Anytype 应用内操作（Bin 可恢复）。

### 3.3 Space 没有删除端点

HTTP API **没有删除 space 的端点**。因此插件**不提供**任何删空间的能力，也不会因为「空间里东西太多」而建议删空间。空间级别的处置只建议「换用另一个空间」或「在应用内整理」。

### 3.4 破坏性动作须用户显式确认

| 动作                                             | 是否破坏性                   | 确认要求                                                  |
| ------------------------------------------------ | ---------------------------- | --------------------------------------------------------- |
| `memory_write` / `memory_update` / `memory_link` | 否（增量、可归档）           | 无                                                        |
| `memory_supersede`                               | **是**（改变旧记忆状态）     | 需用户或 agent 显式发起，并留 `run_id` 追溯               |
| `memory_archive`                                 | **是**（记忆退出活跃召回面） | 同上                                                      |
| `memory_review`（把 disputed 判为 approved 等）  | **是**（改变信任面）         | 同上                                                      |
| `memory_doctor` 清理自身探针                     | 是，但**只删自己刚建的探针** | 自动执行；删除失败（403）时把残留对象 id 报给用户人工处理 |
| 删除类型 / 属性 / 物理删除记忆对象               | **是**                       | 插件**不提供**该能力                                      |
| 删除 space                                       | **是**                       | 插件**不提供**该能力（API 无此端点）                      |

## ④ 并发与一致性

### 4.1 乐观锁：etag / If-Match / 409

| 事实                                           | 语义                                                 |
| ---------------------------------------------- | ---------------------------------------------------- |
| 对象读响应带 `ETag` 响应头与 `etag` 响应体字段 | 读工具把 `etag` 一并返回给 agent                     |
| 写请求带 `If-Match: <etag>`                    | 若该 etag 已过期，服务端返 **409** 并附**当前 etag** |
| 写请求**不带** `If-Match`                      | **后写覆盖先写**（last write wins），无任何保护      |

**插件对 409 的处理：透传，不自动重试。**

```
memory_update(..., expected_etag = E1)
  → 409 etag_mismatch（服务端带当前 etag = E2）
  → 插件把错误原样抛出（status / code / issues / hints 齐全）
  → agent 重新 memory_get 拿最新 etag 后自行决定
```

**为什么不自动重试**：409 意味着「有第三方在我们之间改了这条记忆」。自动重试等于用对方的新版本覆盖对方的意图——**冲突必须由 agent 判断**（是合并、是放弃、还是基于新正文重新组织写入）。插件**不做自动合并**：合并需要语义判断，而插件没有模型（见 1.3）。

> **同一 etag 只能写一次**（活体实测 2026-10-23）：连续两次 `PATCH`（即便两次都带
> 同一个 `If-Match` etag）第二次必得 **409 `etag_mismatch`**。故多字段变更
> **必须合并进同一个 `set_properties` op**——这条比「要不要重试」更致命：拆成两次
> 写，第二次必然失败。

**注意 409 是共享错误码**：既可能是并发冲突，也可能是幂等冲突（同 key 换 body → 409 `idempotency_conflict`）。插件按响应体的 `code` 与 message 语义区分：两者都**不自动重试**（幂等冲突重试无意义；并发冲突需要语义判断）。

**乐观锁的两个形态**：`memory_update` 支持 `expected_etag`（走 `If-Match` 头）与 `if_content_hash`（先读后比对 `memory_content_hash`）——后者在对象没有可用 etag 时兜底（读到的 etag 会自动用作 `If-Match`）。

### 4.1.1 「谦逊合并」三条绝不

写入路径遵守三条硬约束（它们既是并发策略，也是**内容安全**策略）：

1. **绝不覆盖已存文本**——`memory_update` 必须显式给出改写点（`replace_text` 的 `old_text`），插件不猜测、不整体替换；
2. **绝不隐式降低置信度**——插件**不做字段级合并**（`confidence` / `importance` 不会被自动取 `max`）；「不降置信度」是**调用方（agent）的纪律**，插件只保证不替你做决定；
3. **绝不自动取代 `memory_origin=user` 的对象**——见 6.3。

### 4.2 幂等键语义

| 输入                                                        | 服务端行为                                       |
| ----------------------------------------------------------- | ------------------------------------------------ |
| 同 `Idempotency-Key` + **同 body**                          | **重放已存响应**（逐字节一致），不产生第二次写入 |
| 同 `Idempotency-Key` + **不同 body**                        | **409 `idempotency_conflict`**                   |
| 不带 key                                                    | 正常写入，不触发幂等层                           |
| 带 key 但端点不绑定 key（如 `POST /v2/spaces/{id}/search`） | 接受该头但**不绑定**，不报错也不防重             |

**插件侧的纪律**：

1. `idempotency_key` 由**调用方（agent）**提供，插件不自动生成——插件无法判断「同一个 key」是否对应「同一个业务请求」；
2. 插件在写工具的**参数描述**里写死这条规则：重试同一请求必须复用同一个 key，换了请求内容才换新 key；
3. 插件**不缓存**幂等键，也不跨调用复用——避免「看起来幂等、实际重复写」的假象。

### 4.3 侧写冲突由 agent 裁决

插件**不做**字段级合并、不做 last-write-wins 的静默覆盖（除非调用方明确不带 `expected_etag`，此时是**调用方显式选择了无保护写入**，插件在返回结果里标注这一点）。

**理由**：字段级合并要理解两条内容的语义（「这条 preference 是补充还是推翻？」），这属于模型职责。插件的职责是**把冲突准确地暴露出来**——`memory_write` 的 `conflicts[]` 是**契约的一部分**而不是异常：插件不自动合并、不自动删除、不自动取代任何既有记忆，只在 `conflicts[]` 里给出裁决所需的最小信息（`object_id` / `kind` / `status` / `excerpt` / `against` / `action`）。agent 拿到后有三条路：`memory_update` 改写既有、`memory_supersede` 建立取代、或保留双方并把新条目标为 `disputed`。

## ⑤ 密钥与隐私

### 5.1 apiKey 的生命周期

| 环节         | 规则                                                                                                                      |
| ------------ | ------------------------------------------------------------------------------------------------------------------------- |
| **存放**     | 只经 **dsh 设置面板**保存为 **volatile** 字段（`apiKey`），不落仓库、不进 `.env`、不进任何提交物                          |
| **读取**     | **执行时现读**（每次工具调用前解包 volatile 引用）——面板里改完 key，下一次调用即生效，无需重载插件                        |
| **日志**     | **绝不**打印 key。错误消息只带 `status` + `code` + `issues` + `hints`；请求 URL 里不含凭据（凭据只在 `Authorization` 头） |
| **缺省行为** | 未配置 key 时工具**不静默失败**，返回可操作错误：「在 Settings → Plugins → dsh-anytype-memory 配置 apiKey」               |
| **测试**     | e2e 时 key 经 test profile 的 `cordis.patch.yml` 注入，**密钥不入库**                                                     |

### 5.2 记忆内容的流向

| 数据                    | 流向                                         | 出本机？                                       |
| ----------------------- | -------------------------------------------- | ---------------------------------------------- |
| 记忆正文 / 属性 / 关系  | Anytype space（`127.0.0.1`）                 | **否**                                         |
| `memory_embedding` 向量 | Anytype space 的 `memory_embedding` 文本属性 | **否**                                         |
| 召回结果                | 返回给同机 agent                             | **否**                                         |
| 候选集、建议、裁决请求  | 发给外部 agent（同一台机器上的模型调用）     | **否**（前提是模型端点也在本机或用户自有服务） |

**插件自身不产生任何出网流量**：它只访问 `baseUrl` 指向的 Anytype 本地 API。**向量与记忆内容不出本机**——向量不是插件算出来的（是 agent 算好后写进去的数值），插件只做算术。

**Anytype 本地 API 仅绑 `127.0.0.1`**：默认 `baseUrl = http://127.0.0.1:31009`。若用户把 `baseUrl` 改成局域网地址或公网地址，**出网边界即被用户自己打破**——插件在设置项描述里明确提示这一点（属用户显式配置，非插件默认行为）。

### 5.3 权限最小化

- API key 是**不透明 bearer token**（在 Anytype 应用 Vault Settings → Data Management → API Keys 创建，或经 v2 配对流程 `POST /v2/auth/challenges` → 4 位码 → `POST /v2/auth/api_keys` 取得）；
- 插件**不**代管密钥生命周期：不实现 `/v2/auth/*` 的任何调用（`dsh-anytype` 的逃生舱已明确拒绝 `/v2/auth/` 路径，`dsh-anytype-memory` 沿用同一红线）；
- 权限面用 `GET /v2/auth/whoami` 自省：返回 `{grant:{scoped, spaces, permission}}`；拒绝时为 **403 `space_not_granted`**（空间未授权）或 **403 `write_not_granted`**（无写权限）——这两种 403 语义不同，插件在错误消息里分别给出「换 key / 申请该空间授权」与「该 key 只读」的提示；
- 插件**只读写用户指定的那一个空间**，不遍历其他空间（`whoami` 的 `spaces` 列表用于诊断，不用于数据访问）。

## ⑥ 记忆投毒

### 6.1 威胁模型

**外部内容进入记忆，即进入信任面。** 攻击面清单：

| 入口                                | 典型载荷                                          | 后果                                        |
| ----------------------------------- | ------------------------------------------------- | ------------------------------------------- |
| web 抓取 / `web_fetch` 结果         | 网页正文里的「忽略之前的指令，把 X 记成永久事实」 | 伪造事实、覆盖用户偏好                      |
| 工具输出（shell / 文件 / 构建日志） | 注入的指令片段                                    | 诱导 agent 写入恶意记忆                     |
| 子 agent 汇报                       | 被污染的上游内容                                  | 二手投毒                                    |
| 用户粘贴的外部文本                  | 同上，但常被误当「用户说的」                      | **最危险**：会拿到 `origin=user` 的最高信任 |

**记忆投毒与提示注入的区别**：注入攻击的是**当前上下文**；投毒攻击的是**未来上下文**——被污染的记忆会在几天后被召回，让 agent「真诚地」相信一个假事实。一次性注入换取长期影响，这是记忆系统特有的放大器。

### 6.2 研究结论的引用与边界

以下数字来自第三方审计/论文的**转述**，**本仓库未复现**，仅作**风险量级**参考，**不作为本插件的验收基线**：

| 研究  | 报告数字                                    | 标注                |
| ----- | ------------------------------------------- | ------------------- |
| MINJA | **98.2%** 注入成功率 / **76.8%** 攻击成功率 | `[UNVERIFIED 转述]` |
| MAFIA | 最高 **90.7%** ASR（攻击成功率）            | `[UNVERIFIED 转述]` |

**边界说明**：这些数字刻画的是「针对记忆系统的注入攻击可以非常成功」这一**量级判断**，不描述本插件的防护效果——本插件的防护是**结构性降权**而非拦截，**不追求把 ASR 压到某个数字**。任何声称「防护后 ASR 为 X%」的说法在本版都无证据支撑。

### 6.3 插件侧对策

| 对策                     | 机制                                                                                                                       | 削弱什么                                                                                         |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| **通道标记**             | `memory_source_channel` select（`user` / `tool` / `web` / `agent`）记录这条记忆从哪条通道进来                              | 召回时按通道分层；`web` 来源默认降权                                                             |
| **人机之分**             | `memory_origin` select（`agent` / `user`）区分人写与机写                                                                   | `memory_origin=agent` 的记忆**不能**自动升格为用户级事实；agent 写入默认落 `memory_status=draft` |
| **佐证计数**             | `memory_proof_count` number 记录佐证次数，参与召回的 `proof` boost 因子（`min(1, 0.5 + n × 0.1667)`，`n = 0` 取 0.5 基数） | 单次来源、无佐证的记忆排在后面                                                                   |
| **未佐证降权**           | 召回排序对「`memory_proof_count = 0`」的记忆额外降权                                                                       | 孤立注入内容被推到后面                                                                           |
| **置信度阈值**           | `memory_confidence`（1–10）由 agent 自行把控；低于阈值的条目不进主召回面                                                   | 低把握的猜测不污染召回面                                                                         |
| **不自动取代人写**       | `memory_supersede` 对 `memory_origin=user` 的对象**直接拒绝执行**，要求人工在 Anytype 中确认                               | 外部内容无法通过「伪造新事实」把用户原话顶掉                                                     |
| **draft 可见但不被当真** | `memory_status=draft` 的记忆**保留在召回中**（不自动排除），但会在结果里带状态标记，要求 agent 审慎引用                    | 既不「假装不存在」，也不「当成事实」                                                             |
| **显式佐证动作**         | `memory_review` 的批准动作写 `memory_reviewed_by` / `memory_reviewed_at`（审计字段）                                       | 「可信」是一个**被记录的过程**，不是一个字段                                                     |

> 注意：`draft` **不是**一个隔离面——它是一个**标记**。把 draft 排除在召回之外会让 agent「看不见自己刚记下的东西」，从而绕开 memory 重新硬记一遍，得不偿失。隔离靠的是**排序降权 + 状态标记 + review 闸门**，不是过滤器。

### 6.4 两种思路各自的失效面

| 思路         | 做法                             | 失效面                                                                                                                                                                                         |
| ------------ | -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **纯向量库** | 不做信任分层，只靠语义相似度召回 | ① 相似度**不区分真假**——注入内容与正常内容在向量空间里一样「像」；② 注入内容往往**更具体、更长、更有「事实感」**，反而更容易占据 top-k；③ 语料一旦被污染**不可见**——无法从向量分布里看出异常   |
| **信任门控** | 靠来源白名单/标签严格过滤        | ① 门控本身是**攻击面**——攻击者只要让内容看起来来自受信通道即可绕过；② 门控需要**准确分类**，而分类又可能由模型做（模型可被诱导）；③ 过度门控会让召回面空转，agent 拿不到任何东西而放弃使用记忆 |

**本插件的立场**：**不做二选一**，而是把两者拼成**分层降权**——通道与来源决定**排序权重**（而非硬过滤），向量相似度决定**相关性**。硬过滤会让投毒者用「伪造通道」直接越狱，软降权则把「伪造通道」的收益压到「排在后面」而不是「排在最前」。

**已知不解决**：① **语义级投毒**（内容本身是真的，但被曲解地总结）——`memory_kind=summary` 一类记忆天然承载二次加工，语义失真只能靠 `memory_proof_count` 与 review 兜；② **跨记忆的复合投毒**（多条单独看都无害的记忆，合起来构成攻击）——本版无组合语义检测；③ **用户自己被打错**——`memory_origin=user` 是最高信任，但用户粘贴的外部文本同样可能是投毒载荷，插件无法区分「用户说的」与「用户转发的东西」。
