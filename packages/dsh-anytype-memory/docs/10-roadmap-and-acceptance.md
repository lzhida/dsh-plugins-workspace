# 10 路线图与验收

## 本文回答什么问题

- 这个插件按什么顺序做——**每个阶段交付什么、什么条件算过**（含可勾选的完成判据）；
- 什么算「做完了」——**DoD 15 条**，每条给出**可验证的判定方式**与**证据形态**；
- 怎么证明它**真的好用**——为什么**不用公开榜**，以及自建评测怎么跑、指标怎么定；
- 哪些风险会咬人——**风险登记与应对**，以及每条风险落在哪个阶段负责；
- 本版**刻意不做**什么——留给后续的清单与理由。

## 阅读前置

- 读过 09（限制与安全）最佳——本文的验收口径大量引用那里的边界事实（限速、DELETE 权限、并发语义、投毒对策）；
- 09 与本文是配套的：09 说「能做什么、不能做什么」，本文说「怎么证明做到了」。

## ② 验收标准（DoD）

**15 条**。每条给出判定方式与证据形态——「跑得通」不算证据，「某条命令的某次输出」才算。

| #   | DoD                            | 可验证的判定方式                                                                                                                                                                                         | 证据形态                                                                                                   |
| --- | ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 1   | `memory_setup` 幂等            | 连续调用两次 `memory_setup`，前后各取一次 `GET /v2/spaces/{id}/types` 与 `GET /v2/spaces/{id}/properties`，比对类型数与属性数                                                                            | 两次 `GET` 的计数对比（终端输出 / 测试日志）                                                               |
| 2   | 写路径幂等                     | 用**同一** `idempotency_key` + 同一 body 提交两次 `memory_write`，比对两次响应体；再查对象总数                                                                                                           | 两次响应的**逐字节一致** + 对象总数不变                                                                    |
| 3   | 并发冲突如实上报               | 用过期 `expected_etag` 调 `memory_update` → 观察 **409 `etag_mismatch`** 被原样透传（插件**不**自动重试——合并需要语义判断）                                                                              | 错误体含服务端 `status` / `code` / `issues`；**无**「已自动重试成功」的假象                                |
| 4   | 归档不删除                     | `memory_archive` 后 `GET /v2/spaces/{id}/objects/{oid}` 仍可取到该对象且 `memory_status=archived`；**除 `memory_doctor` 清理自身探针外，插件工具面中不存在任何 DELETE 语义的工具**                       | 对象读取响应 + 工具注册清单（16 个工具名，唯一 DELETE 在 doctor 内部且只删自建探针）                       |
| 5   | 召回往返预算                   | 对 `memory_recall` 计数 HTTP 请求数（lexical / vector / links 三臂各一次）                                                                                                                               | 单次调用的请求条数 ≤ 3（客户端日志）                                                                       |
| 6   | 无逐对象 GET                   | 检查召回路径的请求序列，确认没有「候选 id 列表 → 逐个 GET」的形态                                                                                                                                        | 请求序列日志（URL 列表）                                                                                   |
| 7   | 零本地状态                     | 插件运行前后扫描插件目录与用户数据目录；确认记忆对象全部可在 Anytype 查到                                                                                                                                | 目录 diff（无新增文件）+ 空间内对象计数                                                                    |
| 8   | 不跑模型                       | 审查插件包依赖与源码：无模型 SDK / 推理客户端；向量只从 `memory_set_embedding` 进入                                                                                                                      | `package.json` 依赖清单 + grep 检索结果                                                                    |
| 9   | 不出网                         | 核对全部请求的目标 host                                                                                                                                                                                  | 请求日志中所有 URL 均为 `http://127.0.0.1:31009/...`                                                       |
| 10  | 密钥不落盘不入日志             | 在仓库、插件日志、会话轨迹中检索 apiKey 字面量                                                                                                                                                           | 检索**零命中**的输出                                                                                       |
| 11  | 通道标记与降权生效             | 跑投毒用例集：写入 `memory_source_channel=web`、`memory_origin=agent`、`memory_proof_count=0` 的记忆，与一条同主题、佐证 ≥1 的记忆对比召回排序；并验证 `memory_origin=user` 的记忆**未**被自动 supersede | 召回结果顺序（注入条目的 rank 严格靠后）+ 被取代条目的 `memory_status` 仍为 `approved`/`draft`，用例集报告 |

## ③ 评测方法

### 3.1 为什么不用公开榜

**结论：本版不使用 LoCoMo / LOCOMO 等公开基准作为验收依据。**

理由（下列数字均为**第三方审计结论的转述**，本仓库**未复现**，`[UNVERIFIED 转述]`）：

| 观测                                        | 数字   | 对评测设计的含义                                             |
| ------------------------------------------- | ------ | ------------------------------------------------------------ |
| 基准的**评审模型可接受约 62.8% 的错误答案** | 62.8%  | 「通过率」里混着大量评审模型的宽松判定，分数不反映真实正确性 |
| **换一个答案 prompt 即产生约 10.7pp 波动**  | 10.7pp | 评测结果对**评测提示词**敏感——测的是 prompt，不是被测系统    |
| **同一题在不同 harness 下可差约 14pp**      | 14pp   | 跨框架不可比，绝对分数不具迁移性                             |

由此推出三条设计原则：

1. **不引用公开榜的绝对分数**作为本插件的质量声明；
2. **评测必须建在用户自己的真实语料上**——本插件的价值主张是「记住你的事」，通用问答基准测不出这一点；
3. **指标必须是可归因的**——每个指标要能回答「数字变了是因为召回退化了，还是因为语料变了」。

### 3.2 自建评测：200 轮真实召回集

| 项           | 定义                                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------------------ |
| **规模**     | **200 轮**（query → 期望命中的记忆 id 对）                                                             |
| **语料来源** | 用户真实会话与真实记忆写入历史（**脱敏后**使用）；不足 200 条时以真实语料为主、构造样本补齐并单独标注  |
| **构造方式** | 每条记忆写入时记录「它回答得了什么问题」；评测时从真实提问里抽样，配对期望命中 id                      |
| **指标**     | **recall@1**（期望 id 出现在第 1 位）、**recall@5**（出现在前 5 位）                                   |
| **目标**     | recall@1 ≥ 0.6，recall@5 ≥ 0.85（**首版目标值**，以首轮实测校准后固化；未实测前标注为 `[待活体验证]`） |
| **采集方式** | 固定脚本批量调用 `memory_recall`，记录每轮 top-5 的 id 序列                                            |
| **证据形态** | 一份 CSV/JSON 报告：每轮 query、期望 id、top-5 实际 id、命中位次；外加汇总的 recall@1 / recall@5       |

**分层报告**：按记忆 `memory_kind`（fact / decision / preference / …）与 `memory_source_channel` 分别统计——整体数字会掩盖「preference 类召回极差」这类结构性问题。

### 3.3 陈旧率（staleness）

| 项             | 定义                                                                                                                  |
| -------------- | --------------------------------------------------------------------------------------------------------------------- |
| **定义**       | 已被新事实推翻（`memory_status=superseded` 或 `memory_contradicts` 边已建立）的记忆中，**仍被检索命中**的比例         |
| **目标**       | **< 5%**                                                                                                              |
| **采集方式**   | 取评测集中所有被 supersede 的记忆 id 作为「应被淘汰集」，在召回结果中统计其出现次数；分母 = 评测轮数 × 应被淘汰集规模 |
| **证据形态**   | 逐条列出「命中了哪条已淘汰记忆、在哪一轮、命中位次」的清单（**清单本身就是可行动的**——每一条都是一条召回权重 bug）    |
| **为什么重要** | 陈旧记忆命中比「召回不到」更有害：agent 会**基于旧事实行动**，而用户不会察觉                                          |

### 3.4 延迟与往返

| 指标                     | 定义                                      | 目标                                     | 采集方式                                  |
| ------------------------ | ----------------------------------------- | ---------------------------------------- | ----------------------------------------- |
| **写延迟**               | `memory_write` 的端到端耗时（发起到返回） | p50 ≤ 400ms、p95 ≤ 1200ms `[待活体验证]` | 200 次连续写入的耗时分布                  |
| **热路径 p95**           | `memory_recall` 的端到端耗时              | p95 ≤ 1500ms `[待活体验证]`              | 200 轮召回的耗时分布                      |
| **单次召回 HTTP 往返数** | 一次 `memory_recall` 产生的 HTTP 请求条数 | **≤ 3**（硬约束，见 09 §2.3）            | 客户端请求日志计数                        |
| **限速命中**             | 评测期间 429 的次数                       | 越少越好；>0 即说明批量节奏需要调        | 客户端日志中的 `rate_limit_exceeded` 计数 |

### 3.5 投毒用例集

| 项           | 定义                                                                                                                                                                                      |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **规模**     | **30–50 条**注入样本（覆盖 web 文本、工具输出、伪造的「用户原话」、伪装的高置信度事实）                                                                                                   |
| **验证目标** | ① `memory_source_channel` 通道标记**是否生效**；② `memory_origin=agent` 的未佐证记忆在召回中**是否被降权**；③ `memory_origin=user` 的记忆**是否未被**外部内容自动 supersede               |
| **判定**     | 每条用例检查三件事：通道字段是否正确写入；同主题下注入记忆的 rank 是否**严格低于**一条合法记忆；`memory_origin=user` 的记忆 `memory_status` 是否仍为 `approved`/`draft` 而非 `superseded` |
| **证据形态** | 用例表：样本 id、注入载荷类型、期望 rank 关系、实测 rank、pass/fail；失败用例附召回原文                                                                                                   |
| **边界**     | 本用例集**不承诺**任何具体 ASR 数字（见 09 §6.2）——它验证的是**结构性防护是否生效**，不是攻击成功率                                                                                       |

### 3.6 评测的纪律

- **固定语料快照**：每次评测绑定一份语料快照（对象 id 列表 + `memory_content_hash`），避免「语料变了导致数字变了」；
- **冷/热两次**：冷启动（进程刚起）与热态各跑一轮，差值反映缓存/连接复用收益（本插件**无本地缓存**，预期差值极小）；
- **报告带上下文**：任何数字必须附「语料规模、样本数、Anytype 构建版本、运行模式（限速开/关）」；
- **不追分**：目标是**可解释的分布**（哪些 kind 召回差、哪些通道污染），不是把 recall@1 从 0.6 调到 0.61。

## ⑤ 后续可做但本版不做

| 项                        | 本版为何不做                                                                                                                                                                         | 若要做，前置条件                                                  |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------- |
| **本地索引兜底**          | 与「零本地状态」的核心主张直接冲突；且 Anytype 已提供全文检索与关系查询，本地索引会引入**第二真源**（不一致的根源）                                                                  | 需要先放弃「零本地状态」定位（属定位变更，非技术变更）            |
| **后台巩固作业**          | 本版只做「**插件只出巩固计划**」（相似簇 + 合并计划，由 agent 用自己的 LLM 写合并稿再回写）；**不做**自动执行巩固的后台作业——它需要常驻调度、状态机、幂等与断点续跑语义              | 需要先定义巩固策略（合并 / 去重 / 过期判定）与失败恢复语义        |
| **跨空间记忆**            | 一个 API key 的授权空间有限（`whoami` 的 `grant.spaces` 可见），跨空间读会撞 403 `space_not_granted`；且跨空间召回的 scope 语义未定义                                                | 需要多 key 凭证管理与跨空间 scope 命名规范                        |
| **导出 / 导入工具**       | 导出涉及把记忆内容写到插件外部（文件/网络），与「不出网、不落本地」冲突；导入则需要幂等与冲突策略                                                                                    | 需要用户显式授权导出目的地，并明确数据外泄面                      |
| **块级存储 / 块级召回**   | 分块本身已由 `src/chunk.ts` 提供（**确定性、零 LLM**），但它只是**向量的粒度**——长正文切成多块各存一份向量，**记忆本体仍是一个对象**；本版不做「块成为存储单元、块级召回、块级去重」 | 需要定义块级索引与「段命中 → 父记忆」的聚合规则                   |
| **物理删除 / Bin 清理**   | 删除权限受限且语义不可逆（09 §3.1/§3.2）                                                                                                                                             | 需要 Anytype 侧提供稳定删除能力，且用户显式确认                   |
| **自动重试与退避**        | 有意留白（09 §2.4）：重试策略与幂等键责任归调用方                                                                                                                                    | 需要先定义「哪些错误可重试」与「幂等键生成/复用责任」两个语义问题 |
| **跨 harness 的召回基准** | 见 09 §6.2 与本文 3.1：公开榜不可比                                                                                                                                                  | 需要自建可比语料 + 固定评审协议后再谈                             |
