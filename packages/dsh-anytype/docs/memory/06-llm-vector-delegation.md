## 1. 七条硬边界：插件「不做什么」

这七条是**契约级别**的约束，不是实现细节。任何违反都属于设计缺陷，而不是「功能增强」。

| #   | 硬边界             | 插件绝不                                                                                     | 为什么                                                                                                                                  | 怎么检查                                                                                                                      |
| --- | ------------------ | -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 1   | **不跑模型**       | 不调用 LLM、不调用 embedding 模型、**不持有任何模型 API key**                                | 插件是被 agent 调用的工具层；模型属于会话。插件一旦自己持有 key，就变成了第二个模型宿主，密钥面、计费面、失败面同时扩大                 | 插件配置面板里**只有** Anytype 的 `baseUrl` / `apiKey` / 超时等字段，没有任何模型项                                           |
| 2   | **零本地状态**     | 不建 SQLite、不写本地文件、不建本地索引、不落向量缓存                                        | 双写必然漂移；本地状态会把「记忆」变成两份                                                                                              | 磁盘上不存在 `.db` / `.sqlite` / cache 目录；卸载即彻底移除                                                                   |
| 3   | **不改写用户笔迹** | 绝不自动改写 `memory_origin=user` 对象的文本、绝不自动取代它们                               | 用户亲笔写下的东西被机器悄悄替换，是不可接受的信任破坏                                                                                  | `memory_supersede` 对 `memory_origin=user` 旧对象直接拒绝                                                                     |
| 4   | **只归档，不删除** | 除 `memory_doctor` 清理**自己刚建的探针**外，绝不调用 `DELETE /v2/spaces/{id}/objects/{oid}` | 删除不可逆，且 v2 的 DELETE 只对本 API key 创建的对象有效（否则 403 `not_created_by_this_key`）；记忆的错误应该是**被标注**，不是被抹除 | 写路径里没有 DELETE 调用；`memory_archive` 只改 `memory_status=archived`；唯一的 DELETE 在 `memory_doctor` 内部且只删自建探针 |
| 5   | **不跨空间**       | 不在未显式指定的空间里读写；不做跨空间检索                                                   | 空间是用户的边界；串空间会把不相关内容混进召回                                                                                          | 每个空间级工具都接受 `space_id`（或用配置的 `spaceId` / `spaceName` 解析），不遍历其他空间                                    |
| 6   | **不做后台自动写** | 没有定时任务、没有 watch 循环、没有「后台自动抽取并落库」                                    | 自动写意味着在用户不知情时改变记忆库；且写入决策需要 LLM，插件又没有 LLM                                                                | 插件不注册任何定时器；任何写入都必须由一次工具调用显式触发                                                                    |
| 7   | **不倾倒记忆库**   | 任何工具都不提供「导出全部记忆」；召回永远受 `limit` + `max_tokens` 约束                     | 全库进上下文 = 上下文爆炸 + 旧记忆淹没当前任务                                                                                          | 所有工具无「全量导出」参数；`memory_recall` 必带 `truncated` / `omitted_count`                                                |

> 一句话总结：**插件负责「存取与排序」，agent 负责「理解与裁决」。** 插件不做它做不好的事，也不做它不该做的事。

## 2. Agent 侧六步 SOP

新素材（一次对话、一个文档、一段网页）进入记忆库的**标准流程**：

```
① memory_candidates        切块 + 取邻居（确定性、零 LLM）
        │
        ▼
② （agent 侧 LLM）抽取 + 裁决：产出 ADD / UPDATE / DELETE / NONE 事件
        │  ↳ 需要看既有记忆时用 memory_recall / memory_get
        ▼
③ memory_write             落库（带 idempotency_key；读 conflicts[]）
        │
        ▼
④ memory_set_embedding     赋向量（agent 生成，插件只存）
        │
        ▼
⑤ memory_recall            复检：新记忆能否被召回、命中哪几臂
        │
        ▼
⑥ memory_suggest_links → memory_link   织网：关系建议 → 人工/agent 确认后建边
```

### 2.1 逐步说明

| 步  | 工具                                                                             | agent 要做的事                                                                                           | 关键点                                                                                            |
| --- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| ①   | `memory_candidates(text \| source_object_id, space_id, chunk_size, top_k)`       | 把长文本切成候选块，并拿到邻近的既有记忆                                                                 | 插件**不判断**哪块值得记，只提供确定性切块与检索邻居                                              |
| ②   | （LLM，插件不参与）+ `memory_recall` / `memory_get`                              | 从候选块里抽出候选记忆条目；逐条与既有记忆比对，裁决成事件（§4）                                         | **裁决在 agent 侧**；插件只提供 `conflicts[]` 供比对                                              |
| ③   | `memory_write(memories[], idempotency_key)`                                      | 写入被裁决为 `ADD` 的条目；对 `UPDATE` 的条目改走 `memory_update`；对 `DELETE` 的条目走 `memory_archive` | 一次调用带 `idempotency_key`；写完读 `conflicts[]`，必要时补 `memory_supersede` / `memory_update` |
| ④   | `memory_set_embedding(object_id, vector, embedding_model)`                       | 为新写入（或重要既有）记忆生成向量并写入                                                                 | **向量由 agent 生成**；模型名必须与库中既有向量同族（§3.2）                                       |
| ⑤   | `memory_recall(space_id, query, arms, query_vector)`                             | 用与 ① 相同的查询复检：新记忆是否出现、score 是否合理、命中哪几臂                                        | 召回不到就是抽取或写入出了问题，此时应 `memory_update` 补内容而不是重写一遍                       |
| ⑥   | `memory_suggest_links(space_id, object_id)` → `memory_link(from_id, to_id, rel)` | 审阅关系建议，确认后建边                                                                                 | `memory_suggest_links` **只给建议不写**；`rel` 只能是 5 种受控边之一                              |

### 2.2 一次写入的载荷长什么样

第 ③ 步的典型入参（一次调用携带 1–2 条，符合 §5.3 的预算）：

```json
{
  "idempotency_key": "turn-2026-10-23T12-34-56Z-01",
  "memories": [
    {
      "kind": "preference",
      "content": "用户偏好使用 pnpm 而非 npm 管理依赖",
      "name": "用户偏好 pnpm",
      "tags": ["tooling", "pnpm"],
      "source_channel": "user",
      "confidence": 9,
      "importance": 7
    }
  ]
}
```

> `memory_status` 与 `memory_origin` **不接受逐条指定**——前者取配置
> `defaultStatus`（默认 `draft`），后者恒为 `agent`。「这条是用户亲口说的」目前
> 只能由**人工在 Anytype 里改写** `memory_origin` 来表达（见《02 记忆模型》§4.1）。
>
> 写完**立刻自查能否召回**要留个心眼：Anytype 的**全文索引是最终一致的**，
> 刚写的对象可能要等约 3～6s 才被搜到（活体实测 2026-10-23 / 2026-10-24）。

对应的第 ④ 步（向量由 agent 生成后写入）：

```json
{
  "object_id": "3f9a...",
  "vector": [0.031, -0.118, 0.044, 0.207, 0.512],
  "embedding_model": "bge-m3"
}
```

> 上例的 `vector` 只列前 5 个分量；真实调用是 **768 个数字**。

### 2.3 何时可以跳过

| 情况                     | 允许的简化                                                                      |
| ------------------------ | ------------------------------------------------------------------------------- |
| 只是回答问题，不需要沉淀 | 直接用 `memory_recall`，不做 ①③④⑥                                               |
| 用户明确说「记住这条」   | 跳过 ①（内容已给），但**必须**做 ③；向量可选（不做则该条只在 lexical 臂可召回） |
| 一次性问答               | 不写任何记忆（预算纪律，见 §5）                                                 |

## 3. 向量协议

### 3.1 存储格式

`memory_embedding` 是一个 **text 属性**，值是 **Float32Array 的 base64**：

```
memory_embedding = base64( Float32Array(v1, v2, ..., vN) )      // 小端 float32
```

| 维度                                   | 数值                                             |
| -------------------------------------- | ------------------------------------------------ |
| 768 维 float32 原始体积                | 768 × 4 = **3072 B**                             |
| base64 后体积                          | ≈ **4096 字符 ≈ 4.1 KB**（含末尾填充与属性开销） |
| 1536 维（`text-embedding-3-small` 类） | 6144 B → base64 ≈ **8.2 KB**                     |

配套两个属性：

| 属性                     | 类型   | 含义                                           |
| ------------------------ | ------ | ---------------------------------------------- |
| `memory_embedding_model` | text   | 向量所属模型（**含变体后缀**，见 §3.2）        |
| `memory_embedding_dim`   | number | 存储向量的**实际长度**（降维后写降维后的长度） |

> 属性显示名一律 `Memory ` 前缀（key 派生为 `memory_*`）——否则会与空间内置属性撞
> 「同名不同格式」→ 400 `property format conflict`（活体实测 2026-10-23）。
> 详见《02 记忆模型》§2.0。

### 3.2 绑定：模型 + 维度 = 向量空间

> **不同模型或不同维度的向量不可混用。混用会静默污染结果**——余弦算出来仍有数值，但排序毫无意义，且**没有任何报错**。

因此：

| 规则                              | 实现                                                                                                                                                                             |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 模型名进 `memory_embedding_model` | 变体信息也进模型名：`bge-m3` / `bge-m3#i8` / `bge-m3#i8r256` 天然是不同的「空间」                                                                                                |
| 维度进 `memory_embedding_dim`     | 参与同一套排除判定                                                                                                                                                               |
| 排除规则                          | 召回时，若候选的 `memory_embedding_model` ≠ 本次 `embedding_model`，或 `memory_embedding_dim` ≠ `query_vector.length` → **该候选被排除**，并在 `warnings[]` 里报告剔除条数       |
| 写入侧                            | `memory_set_embedding` 发现对象已有**模型不同或维度不同**的向量 → **抛错拒绝**（不覆盖、不静默混写）                                                                             |
| 换模型怎么办                      | 换模型 = 换向量空间。旧向量必须**重算**（agent 重新生成并覆盖写），不能新旧混用；插件提供 `memory_set_embedding` 覆盖写路径，但**不会**自动批量重算（那是 agent 的活，且要花钱） |

### 3.3 读取与投影

```
POST /v2/spaces/{id}/search
body: { "query": "",
        "fields": ["memory_embedding", "memory_embedding_model", "memory_embedding_dim", "memory_kind", "memory_status", "memory_origin", "memory_confidence", "memory_proof_count"] }
```

| 规则     | 值                                             | 理由                                                                              |
| -------- | ---------------------------------------------- | --------------------------------------------------------------------------------- |
| 单批行数 | **≤ 20 行/请求**                               | 20 × 4.1 KB ≈ 82 KB，单响应可控；Anytype 文本属性也可能有长度上限                 |
| 批数     | `ceil(候选数 / 20)`                            | 超过 3 次往返需 agent 显式驱动（限速 1 req/s，见 `05-anytype-as-source.md` §5.8） |
| 解码     | base64 → `Uint8Array` → `Float32Array`（小端） | 插件内计算余弦，**不落盘**                                                        |
| 打分     | 余弦相似度（维度不符或零向量一律取 0）         | 线性可比，直接作为该臂 relevance                                                  |

### 3.4 向量永不出现在返回值里

**任何工具的返回值都不包含 `memory_embedding` 原值**：

| 工具                                                    | 处理                                                                                        |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `memory_recall`                                         | item 里只给 `score` / `arms_hit`，**绝不给向量**                                            |
| `memory_get`                                            | `properties` 里保留 `memory_embedding_model` / `memory_embedding_dim`，向量原值由工具层剔除 |
| `memory_list` / `memory_stats` / `memory_suggest_links` | 不投影 `memory_embedding`                                                                   |
| `memory_doctor`                                         | 只报告 schema 与能力，不读向量内容                                                          |

理由：向量是**大**（每条 4 KB 起）且**无用**（对 agent 没有可解释性）；把它塞进上下文会挤爆预算。它只是插件内部的排序中间量。

### 3.5 降级链：属性长度上限咬人时怎么办

若 Anytype 文本属性的长度上限导致 `memory_embedding` 写不进去（报错或截断），按顺序降级：

| 级  | 方案                                                | 体积（768 维）                                        | 代价                                     | 状态           |
| --- | --------------------------------------------------- | ----------------------------------------------------- | ---------------------------------------- | -------------- |
| 1   | **基线**：float32 + base64                          | ≈ 4.1 KB                                              | 无                                       | 默认           |
| 2   | **int8 量化**：每维 1 字节 + 1 个 float32 scale     | 768 B → base64 ≈ **1.0 KB**                           | 精度损失（余弦排序基本不变，绝对值略偏） | 可用           |
| 3   | **降维到 256**（PCA / 随机投影，**由 agent 计算**） | 256 × 4 B → base64 ≈ **1.4 KB**（或量化后 ≈ 0.35 KB） | 牺牲细粒度区分度                         | 可用           |
| 4   | **分片属性**：`memory_embedding_1..n`               | 每片 ≤ 属性上限                                       | 需要 schema 扩展；插件读取时按序号拼接   | `[待活体验证]` |

**降级链的实现约定**

| 约定                   | 内容                                                                                                                                                                                                     |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 格式标记               | `memory_embedding` 的二进制负载带 4 字节 magic：`F32`（float32）/ `I08`（int8 + 4 字节 scale）；量化格式的 scale 紧随其后                                                                                |
| 变体名                 | `memory_embedding_model` 记 `bge-m3#i8`、`bge-m3#i8r256`——变体即独立向量空间（§3.2）                                                                                                                     |
| `memory_embedding_dim` | 记**存储后**的长度（768 / 256）                                                                                                                                                                          |
| 降维责任               | **agent**：插件不跑模型，不做 PCA、不做随机投影                                                                                                                                                          |
| 分片属性               | `memory_embedding_1`、`memory_embedding_2`…（text）；读取端按数字序号拼接。**这是对 `03` 系列 schema 文档的扩展项**，`[待活体验证]`：需确认 Anytype 对「同前缀多属性」的检索与投影行为，以及属性数量上限 |

**长度上限的验证方式**：`[待活体验证]` ——用 `memory_set_embedding` 写入一个 8 KB 的 `memory_embedding`（768 维量化前 + 冗余），观察是截断、报错还是接受；同时 `GET /v2/spaces/{id}/properties` 确认 `memory_embedding` 的 `format` 与是否标注长度约束。

## 4. 写事件词表（Mem0 风格）

抽取阶段，agent 对**每一条候选记忆**给出一个事件，词表沿用 Mem0 的四值：

| 事件     | 含义                                               | 落到哪个工具                                                           | 插件行为                                                                                                       |
| -------- | -------------------------------------------------- | ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `ADD`    | 全新知识，库里没有                                 | `memory_write`                                                         | 创建新对象                                                                                                     |
| `UPDATE` | 既有记忆需要修订（内容补充、状态推进、置信度提升） | `memory_update`（`replace_text` / `insert_blocks` / `set_properties`） | 局部改写；**不覆盖无关段落**；只有正文真的改了才动 `memory_content_hash`                                       |
| `DELETE` | 既有记忆已失效                                     | **`memory_archive`**                                                   | ⚠️ **在本插件中被降级为「归档」，绝不真删**（硬边界 ④）；`reason` 只回传给调用方，**不写回正文**（正文不可变） |
| `NONE`   | 不值得记（重复、无价值、推测未证实、临时状态）     | 无                                                                     | **不产生任何写入**——`NONE` 是最常见的正确答案                                                                  |

### 4.1 决策权归属

> **agent 决定，插件只报告。**

| 层    | 职责                                                                                                                                 |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------ |
| agent | 判断 `ADD` / `UPDATE` / `DELETE` / `NONE`；决定是否合并、是否取代                                                                    |
| 插件  | 提供 `conflicts[]`（既有相近记忆的 id / kind / status / valid_from / snippet）；提供去重结果 `deduped[]`；**不裁决、不合并、不删除** |

### 4.2 事件与工具的映射表

| 事件     | 工具调用         | 幂等键                                  | 冲突处理                                                                  |
| -------- | ---------------- | --------------------------------------- | ------------------------------------------------------------------------- |
| `ADD`    | `memory_write`   | 必带（建议 uuid 或「本次抽取批次 id」） | `conflicts[]` 非空 → agent 决定 merge / supersede / 保留双份              |
| `UPDATE` | `memory_update`  | 不适用（PATCH 由 etag 保护）            | etag 冲突 → 重读后重试一次（插件自动）；仍冲突 → 返回 `conflict` 给 agent |
| `DELETE` | `memory_archive` | 不适用                                  | 幂等：已 archived 直接返回成功                                            |
| `NONE`   | 无               | —                                       | —                                                                         |

## 5. 记忆写入白名单与预算

### 5.1 白名单：该记什么

| 类别             | 判定标准                                         | 例子                                                           |
| ---------------- | ------------------------------------------------ | -------------------------------------------------------------- |
| **稳定偏好**     | 下次还会成立，且用户明确表达过                   | 「偏好 pnpm 而非 npm」「回答用中文」                           |
| **带理由的决策** | 决策**连同理由**一起记，否则半年后没人知道为什么 | 「记忆层用 Anytype 作真源，因为实测 API 已覆盖全文检索与过滤」 |
| **持久事实**     | 不随会话失效的环境/项目事实                      | 「本机 Anytype API 端口 31009」「仓库是 pnpm workspace」       |
| **硬教训**       | 踩过的坑 + 正确做法                              | 「`fields` 是投影不是裁剪，传了反而变大」                      |
| **可复用流程**   | 会重复执行的多步操作                             | 「e2e 四步：profile → 安装 → 预检 → 三断言」                   |

### 5.2 反白名单：不该记

| 不记                                        | 原因                                                                                  |
| ------------------------------------------- | ------------------------------------------------------------------------------------- |
| 临时状态（当前分支、今天的 TODO、临时端口） | 明天就过期，过期记忆会污染召回                                                        |
| 一次性任务细节                              | 无复用价值                                                                            |
| 未经验证的推测                              | 记忆的价值在于**可信**，不是在于**多**                                                |
| 与既有记忆重复的内容                        | `memory_content_hash` 去重 + `conflicts[]` 机制已经处理                               |
| 密钥 / 令牌 / 凭据 / 个人信息               | 安全边界；`memory_origin=user` 的私密内容也不该被 agent 复述到别处                    |
| 整段原文（长文档）                          | 记忆是**提炼**不是**搬运**；原文留在 Anytype 自己的对象里即可，用 `source` 关系指过去 |

### 5.3 预算：一轮 1–2 条

| 规则     | 说明                                                                                             |
| -------- | ------------------------------------------------------------------------------------------------ |
| 目标     | **每轮对话 1–2 条写入**                                                                          |
| 上限     | 一轮内 `memory_write` 携带的条目 **≤ 2**（工具本身允许 1..50，但那是给「批量导入既有记忆」用的） |
| 优先级   | 有价值 > 没价值；有理由 > 没理由；稳定 > 临时                                                    |
| 宁缺毋滥 | `NONE` 是正常且常见的结果——一轮零写入不代表失败                                                  |
| 写前先查 | 写入前先 `memory_recall` 看是否已有相近记忆，避免重复堆积                                        |

> 记忆库的价值随**信噪比**增长，而不是随条数增长。每轮 1–2 条、命中率高，半年后是一份可信的资产；每轮 5 条、半数是 `NONE` 的边角料，半年后是一堆噪音。

## 6. 投毒防御

外部内容（网页、工具输出、他人文档）进入长期记忆，等于把攻击面带进了 agent 的未来所有会话。四道防线：

### 6.1 来源标记：`memory_source_channel`

| 值      | 含义             | 典型来源                 |
| ------- | ---------------- | ------------------------ |
| `user`  | 用户亲口说的     | 对话中的用户陈述         |
| `tool`  | 工具执行结果     | 命令输出、文件内容       |
| `web`   | 外部网络内容     | 网页、搜索结果、API 响应 |
| `agent` | agent 自己的推断 | 模型生成的结论           |

- 每条记忆都带 `memory_source_channel`——**来源可见**是防御的第一步；
- `web` 来源的记忆**默认不被自动提升**（见 §6.3 的佐证计数）。

### 6.2 人类 vs 机器：`memory_origin`

| 值      | 含义     | 保护规则                                       |
| ------- | -------- | ---------------------------------------------- |
| `user`  | 人写的   | **插件绝不自动改写、绝不自动取代**（硬边界 ③） |
| `agent` | 机器写的 | 可被 agent 自动更新/取代                       |

- `memory_origin=user` 的记忆是**信任锚点**——agent 的自动流程绕不开它；
- `memory_origin=agent` 的记忆是**草稿**——可以被更好的证据推翻；
- **写入路径恒定写 `agent`**：`memory_write` 不接受逐条指定 `origin`，人写的条目只能来自人工在 Anytype 里改写——这条防线不被 agent 自己绕开。

### 6.3 佐证计数：`memory_proof_count`

| 规则     | 说明                                                                                                                           |
| -------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 计数     | 每出现一次**独立的**佐证（用户再次确认、另一个来源印证），`memory_proof_count += 1`                                            |
| 参与排序 | `proof(d) = min(1, 0.5 + proof_count × 0.1667)`（见 `05-anytype-as-source.md` §5.5）                                           |
| 未被佐证 | `memory_proof_count = 0` → 因子取 **0.5 基数**：被**降权**，但**不被排除**（降权是排序信号，排除是删除判断，插件不越权做后者） |
| 佐证来源 | 只统计 `memory_source_channel` **不同**的佐证；同一来源重复出现**不重复计数**——否则攻击者可以用同一份网页刷佐证                |

### 6.4 写入前的怀疑

| 检查                                                              | 动作                                                               |
| ----------------------------------------------------------------- | ------------------------------------------------------------------ |
| 内容是否包含**指令性语句**（"ignore previous instructions" 之类） | 不得作为**记忆内容**写入；`web` 来源且含指令的片段，直接 `NONE`    |
| 是否试图**重定义身份/权限**（"从今以后你必须…"）                  | `NONE`——记忆不是授权通道                                           |
| 是否与既有 `memory_origin=user` 记忆**矛盾**                      | 走 `conflicts[]` 裁决路径，绝不自动覆盖用户笔迹                    |
| 是否包含凭据                                                      | `NONE`，且不写入任何 `source` 引用链                               |
| 置信度                                                            | `web` 来源默认 `confidence ≤ 5`（10 分制）；只有被佐证后才允许上调 |

## 7. 责任边界速查

| 关注点             | 插件负责                                  | agent 负责                            |
| ------------------ | ----------------------------------------- | ------------------------------------- |
| 抽取记忆条目       | ❌                                        | ✅（LLM 抽取）                        |
| 判断新旧/冲突      | 报告 `conflicts[]` / `deduped[]`          | ✅（裁决 merge / supersede / create） |
| 生成向量           | ❌（只存）                                | ✅（调 embedding 模型）               |
| 相似度计算         | ✅（进程内余弦）                          | ❌                                    |
| 融合与排序         | ✅（RRF + boost）                         | ❌                                    |
| 落库 / 建边 / 归档 | ✅（受约束地执行）                        | ✅（决定要不要执行）                  |
| 改写用户原话       | ❌（永不自动）                            | ✅（显式 `memory_update`）            |
| 删除记忆           | ❌（只归档）                              | ✅（决定归档谁）                      |
| 控制上下文体量     | ✅（`max_tokens` 截断 + `omitted_count`） | ✅（决定用哪几臂、给多少预算）        |
| 决定「值不值得记」 | ❌                                        | ✅（白名单 + 每轮 1–2 条预算）        |

---

## 8. 一句话小结

> **插件是一双手，不是一个脑袋。**
> 它负责把记忆**准确地存取、可靠地排序、克制地呈现**；把「什么值得记、这条对不对、怎么合并、要不要取代」的判断权**完整地留给 agent**。
> 一切不可逆的操作（改写用户笔迹、删除记忆、跨空间、后台自动写）都留在人类手里；一切消耗 token 的操作（向量、全库倾倒）都被显式预算约束。
