## 逐字一致性机制（卡片 2/6 调整）

第 1/6 张卡建立了「63 个 vendored 文件与上游逐字一致」的内容级不变量。第 2/6 张卡
必须改上游 `src/host/tools.ts` 与 `src/index.ts`，该不变量随之调整为**三段式**；
看板官方集成系列 1/3 张卡（worktree 改用官方服务）沿用同一套三段式登记，只是例外
从 2 个文件扩大到 15 个。

1. **`docs/upstream-sha256.txt`**：永远是上游原始哈希，一个字节都不许改写；
   其自身的 sha256 被契约测试钉死（`UPSTREAM_MANIFEST_SHA256`），被改写即失败。
2. **`docs/local-patches.json`**：登记表——每个被有意改动的上游文件都必须登记
   路径、上游原始 sha256 与改动理由；未登记的文件仍与上游逐字一致。
3. **`docs/local-sha256.txt`**：被改动文件的当前本地哈希（`sha256sum` 同款格式）。

契约测试（`src/local/package-contract.test.ts`）据此逐项核对：

- 未登记文件：当前哈希 **必须等于** 上游清单中的哈希；
- 已登记文件：登记的上游哈希 **必须等于** 上游清单中的哈希（清单没被偷改），
  且当前哈希 **必须等于** `docs/local-sha256.txt` 中的哈希；
- `local-patches.json` ↔ `docs/local-sha256.txt` ↔ 上游清单三者**双向一致**
  （漏登记、多登记、漏哈希、多哈希都报错）；
- 文件集仍双向一致（`src/` 除 `src/local/` 外与上游清单一一对应，63 个文件）。

即：**例外必须显式登记且可核验，任何未登记的额外改动仍会立刻被捕获。**

## 已知缺口

- **上游测试未随 npm 包发布**（`files` 不含 `*.test.ts`，上游仓库另有 60 个
  `tests/*.spec.ts`）。本卡未联网从 GitHub 拉取，vendored 副本**零上游测试**；
  行为回归由本仓 `src/local/` 契约测试 + 卡 6/6 的实机 e2e 覆盖。
- 上游 `tsdown.*.config.ts` / `vitest.config.ts` / `tsconfig.json` 同样不在 npm
  包内，已用本仓等价配置替代（见第 3、7 条）。
- `files` **不含 `tsconfig.json` / `tsconfig.vendored.json`**（两者 `extends` 仓库根
  `tsconfig.base.json`，发布 tarball 内该路径不存在，`npm run typecheck` 会在
  tarball 内失败）。构建不受影响：构建脚本已用 `tsconfigRaw` 内联编译选项，
  实测在「无 tsconfig」环境下重建可得到与工作区**字节一致**的产物。
- **建卡强制隔离的边界**（验收联动 1/4 已知限制）：强制只覆盖**新建卡**路径
  （工具入口 / 板服务入口 / GUI 建卡入口）。① **改卡**（`taskboard_update` 与 GUI
  改卡处）维持上游口径按传入值写入，不受强制约束；② **既有旧卡**的隔离字段不被
  追溯改写；③ **台账导入**（`validateLedgerImport`）不经建卡路径，同样不受强制
  约束；④ GUI 建卡表单仍展示 `none` 选项（提交后被服务端强制为 worktree，客户端
  尚未展示 `isolationForced` / `isolationNote` 注记字段）；⑤ 官方 worktree 服务
  缺席时，执行层按上游口径降级到原目录执行（`src/host/execution.ts`），此时
  worktree 隔离只在**建卡计划**层面成立，实际执行目录仍为原目录。
